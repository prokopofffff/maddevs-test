# Главная страница: каталог событий, поиск, фильтры, вход участника

Дизайн-документ по итогам обсуждения с пользователем 2026-10-22. Из него строится план реализации. Правила потом переносятся в `docs/SPEC.md` и в новые записи `docs/DECISIONS.md` (D-036: SPEC — контракт, мотивировка — в DECISIONS).

Пометки:
- **(польз.)** — решил пользователь;
- **(агент)** — решение агента, его можно пересмотреть;
- без пометки — следствие из уже принятых решений.

## 1. Зачем

Сейчас `/` перенаправляет на `/organizer`, а без сессии оттуда отправляет на экран входа. Посетителю на главной делать нечего: событие находят только по ссылке, которой поделился организатор. Пользователь хочет, чтобы главная стала общей точкой входа в приложение. На ней список событий всех организаторов с поиском и фильтрами, а в шапке — вход для участника и для организатора. **(польз.)**

Участник после входа видит в одном месте все свои регистрации, текущие и прошлые, со статусами. Искать личные ссылки в почте больше не нужно. **(польз.)**

## 2. Что меняется в принятых решениях

- **Публичный каталог** в `docs/SPEC.md` (раздел 0) записан как «вне рамок». Это снимается: каталог есть. Нужна новая D.
- **У участника появляется вход** (D-007: «участник без аккаунта»). Аккаунта и пароля по-прежнему нет. Вход — это сессия, привязанная к подтверждённому кодом email. Нужна новая D, которая уточняет D-007.
- **Возраст события** (D-008: «минимальный возраст 1–120 или null») меняется на шкалу. Нужна новая D, которая уточняет D-008.
- **Новые поля события:** формат, город, адрес, категория. Нужна новая D.

## 3. Цели

1. `/` — каталог: поиск, фильтры-чипы, сетка карточек. **(польз.)**
2. В шапке на всех публичных страницах две кнопки: «Мои регистрации» (вход участника) и «Организаторам» (вход организатора и поддержки). **(польз.: шапка из варианта B)**
3. Вход участника — по email и коду из письма, тем же способом, что при регистрации на событие. **(польз.)**
4. Профиль участника: текущие и прошедшие регистрации со статусами. **(польз.)**
5. Участник, который вошёл, регистрируется на событие без кода. **(польз.)**
6. У события есть формат, город, адрес, категория и возраст по шкале. Всё это видно в карточке и на странице события, по всему есть фильтры. **(польз.)**

## 4. Не цели

- Справочник городов, автодополнение и геокодинг адреса, карта, фильтр «рядом со мной». Город и адрес — свободный текст **(польз.)**. Проблема записана в DEVLOG от 2026-10-22 21:17.
- Ссылка на трансляцию у онлайн-события: такого поля нет, организатор пишет ссылку в описании **(польз.)**. В README «Состояние проекта» это называется прямо.
- Аккаунт участника с паролем, редактирование профиля, смена email.
- Скрытые события «только по ссылке»: в каталоге все события **(польз.)**.
- Избранное, подписки на организатора, публичная страница организатора.
- Номера страниц в каталоге, сортировка по выбору пользователя.

## 5. Анти-цели

Если случится что-то из этого, работа провалена, даже если формально всё работает.

- Ломаются старые входы без логина. `/e/:id` с регистрацией по коду, «Уже регистрировались?» и `/r/:token` работают для гостя как раньше. Ссылки из старых писем открываются.
- Каталог или профиль раскрывают, кто зарегистрирован. Список регистраций email доступен только после верного кода на этот email. В публичных ответах нет ни email, ни имён. Свойство D-048 «без кода не узнать, есть ли регистрация» сохраняется: код входа уходит на любой email.
- Вход участника открывает организаторские или поддержечные маршруты. Сессия участника — отдельная сущность, `requireUser` и `requireRole` её не принимают.
- Обходится проверка возраста или «одна неотменённая регистрация на (событие, email)» при регистрации без кода. Регистрация без кода идёт тем же `allocate` под блокировкой события (D-011).

## 6. Модель данных

### 6.1 `events`: новые и изменённые колонки

| Колонка | Тип | Правило |
|---|---|---|
| `format` | `text` | `offline` \| `online` **(польз.)** |
| `city` | `text null` | у `offline` обязателен, 1–100 символов после trim и схлопывания пробелов; у `online` — `null` **(польз.)**. Check-ограничение на пару `format`/`city` **(агент)** |
| `address` | `text null` | у `offline` обязателен, 1–300 символов после trim; у `online` — `null` **(польз.)** |
| `category` | `text` | `meetup` \| `workshop` \| `lecture` \| `conference` \| `game` \| `other` (митап, воркшоп, лекция, конференция, игра, другое) **(польз.)** |
| `min_age` | `integer not null default 0` | `check (min_age in (0, 6, 12, 16, 18))`; 0 — «0+», без ограничения **(польз.: шкала; агент: 0 вместо null)** |

Индексы **(агент)**: `(starts_at, id)` для ленты каталога и курсора; `(lower(city))` для списка городов и фильтра.

**Миграция существующих строк (агент):**
- `min_age`: `null` → 0. Остальные значения округляются вверх до ближайшего значения шкалы, всё выше 18 становится 18 (14 → 16, 21 → 18). Значения выше 18 при этом ослабляют ограничение. Сейчас данные есть только в демо и dev, потери на практике нет.
- `format = 'online'`, `city` и `address` — `null`, `category = 'other'`: так строки проходят check-ограничения. Сид после миграции пишет настоящие значения.

### 6.2 Вход участника

**`email_verifications`:**
- `purpose` пополняется значением `login`;
- `event_id` становится `null`able: у `login` его нет, у `register` и `lookup` он обязателен (check);
- лимит «не чаще раза в минуту» для `login` считается по email среди кодов `login`;
- 10 минут жизни, 5 попыток, гашение предыдущего кода — как у остальных назначений (D-007, D-039).

**Новая таблица `participant_sessions` (агент):**

| Колонка | Тип | Правило |
|---|---|---|
| `id_hash` | `text` | PK, SHA-256 от значения cookie (как `sessions`, D-040) |
| `email` | `text` | нормализованный (`trim`, `toLowerCase`) |
| `created_at`, `expires_at` | `timestamptz` | 30 дней, как D-005 |

- Cookie отдельная, `participant_session`, с теми же флагами, что у сессии организатора (httpOnly, `SameSite=Lax`).
- Человек может одновременно быть организатором и участником под одним email: две сессии живут независимо.

**`registrations`:** индекс `(email, created_at desc)` для профиля **(агент)**.

## 7. API

Общие правила: zod-схемы, `hc`-клиент (D-024), rate limit на все запросы (D-006). Коды ошибок пишутся в стиле SPEC.

### 7.1 Каталог (без входа)

`GET /events` — query-параметры **(агент: состав; польз.: набор фильтров)**:

| Параметр | Значения | Правило |
|---|---|---|
| `q` | строка до 100 символов | `ILIKE` по `title` и `description`, спецсимволы `%` и `_` экранируются. Без полнотекстового поиска (агент) |
| `when` | `upcoming` (по умолчанию) \| `past` \| `today` \| `week` | `upcoming` — `starts_at > now`; `past` — `starts_at <= now`; `today` и `week` — подмножество `upcoming` |
| `tz` | IANA-пояс браузера | границы «сегодня» и «на неделе» (до конца седьмого дня, считая сегодняшний) считаются в поясе посетителя, а не события (агент) |
| `hasSeats` | `1` | `freeSeats > 0`. Событие с листом ожидания не проходит |
| `format` | `offline` \| `online` | |
| `city` | строка | сравнение по `lower(city)` |
| `category` | значение перечня | |
| `maxAge` | 0 \| 6 \| 12 \| 16 \| 18 | `min_age <= maxAge`; «до 12+» показывает 0+, 6+ и 12+ (польз.) |
| `cursor` | непрозрачная строка | |

- Порядок: `upcoming`, `today` и `week` — по возрастанию `starts_at`; `past` — по убыванию.
- Страница — 24 события. Курсор — `(starts_at, id)`. В ответе `nextCursor` или `null` (агент).
- Ответ: `200 {events: [{id, title, startsAt, timezone, format, city, category, minAge, freeSeats, started}], nextCursor}`. Адреса и описания в списке нет.
- `freeSeats` считается тем же способом, что в `GET /events/:id` (D-026).

`GET /events/cities` — `200 {cities: string[]}`: города офлайн-событий из `upcoming`, без учёта регистра. Показывается написание самого раннего события, сортировка по алфавиту (агент).

`GET /events/:id` дополнительно отдаёт `format`, `city`, `address`, `category`. `minAge` теперь число из шкалы, 0 вместо `null`.

### 7.2 Вход участника

| Метод и путь | Тело | Ответ | Ошибки |
|---|---|---|---|
| `POST /participant/verifications` | `{email}` | `201 {verificationId, expiresAt, resendAfter}` | `429 code_resend_too_soon {retryAfter}` |
| `POST /participant/verifications/:id/confirm` | `{code}` | `200 {email}` и cookie `participant_session` | `400 code_invalid {attemptsLeft}`, `410 code_expired`, `410 code_attempts_exceeded` |
| `GET /participant/me` | — | `200 {email, lastData: {firstName, lastName, birthDate} \| null}` | `401` |
| `POST /participant/logout` | — | `204` | — |
| `GET /participant/registrations` | — | `200 {registrations: [{token, status, waitlistPosition?, ticketCode, checkedInAt, cancelledAt, event: {id, title, startsAt, timezone, format, city, started}}]}` | `401` |

- Код уходит на любой email, даже если регистраций у него нет. Письмо — новый тип `login_code` в outbox, с немедленным пинком (D-013, D-014).
- `lastData` — данные последней по `created_at` регистрации этого email. Ими предзаполняется форма (агент).
- `GET /participant/registrations` отдаёт все строки этого email, включая отменённые. Повторная регистрация после отказа даёт вторую строку (D-007), и обе видны.

### 7.3 Регистрация без кода

`POST /events/:id/registrations` под сессией участника. Тело — `participantDataSchema {firstName, lastName, birthDate}`. Email берётся из сессии.

- Ответ тот же, что у `confirm` с `purpose = register`: `200 {result: "confirmed" | "waitlisted" | "existing", token, status, waitlistPosition?}`.
- Ошибки: `401` без сессии, `409 registration_closed`, `422 below_min_age {minAge}`.
- Проверки и `allocate` — те же функции и та же транзакция под блокировкой события. Письма `confirmed` и `waitlisted` уходят так же (D-011, D-012, D-013).

Для участника, который вошёл, «Уже регистрировались?» на `/e/:id` не нужно. Если у его email есть неотменённая регистрация на это событие, страница показывает ссылку на неё. Для этого `GET /events/:id` под сессией участника отдаёт `myRegistration: {token, status} | null` (агент).

### 7.4 Организатор

В `eventInputSchema` и `eventPatchSchema` добавляются `format`, `city`, `address`, `category`. `minAge` становится значением шкалы, по умолчанию 0.
- Правка `format` с `offline` на `online` обнуляет `city` и `address`.
- Повышение `minAge` даёт прежнее предупреждение «N участников не проходят по возрасту» (D-017).
- Письма о переносе при смене адреса нет: перенос — только смена времени (D-016) (агент).

## 8. Экраны

Стили — токены и классы `docs/design/template.html` (D-025, D-027), без UI-кита. Интерфейс на русском. Каталог и профиль — mobile-first, как экран участника.

### 8.1 Шапка публичных страниц

Используется на `/`, `/e/:id`, `/r/:token`, `/me`.

| Кто | Справа в шапке |
|---|---|
| гость | «Мои регистрации», «Организаторам» (акцентная) |
| участник | «Мои регистрации», `email · Выйти` |
| организатор | «Мои регистрации», «Мои события» (акцентная, на `/organizer`), `email · Выйти` |
| поддержка | «Мои регистрации», «Поддержка» (акцентная, на `/support`), `email · Выйти` |

«Мои регистрации» видна всегда: организатор тоже может быть участником под своим или другим email (агент).

- «Организаторам» ведёт на существующий `/login`. Поддержка входит там же (агент).
- Если есть обе сессии, участника и организатора, показываются обе кнопки и один `Выйти` для каждой (агент).
- Макет: `.context/.superpowers/brainstorm/…/content/main-combined.html` (вне репозитория).

### 8.2 `/` — каталог

Сверху вниз:
1. Поиск по названию и описанию.
2. Ряд чипов: «Предстоящие» / «Прошедшие» (взаимоисключающие), «Сегодня», «На неделе», «Есть места».
3. Ряд фильтров: «Офлайн» / «Онлайн» (чипы), «Город ▾», «Категория ▾», «Возраст ▾» (любой, 0+, до 6+, до 12+, до 16+, до 18+), «Сбросить».

Под фильтрами — сетка карточек: 3 колонки на ноутбуке, 1 на телефоне. В карточке:
- категория и город (или «Онлайн»);
- название;
- дата и время в поясе события с подписью смещения (D-015);
- плашка «Осталось N мест» / «Лист ожидания» / «Регистрация закрыта» (у прошедших);
- плашка возраста.

Клик ведёт на `/e/:id`.

**Поведение (агент):**
- Фильтры и поиск живут в query-параметрах адреса, поэтому подборкой можно поделиться ссылкой, а «Назад» её восстанавливает.
- Поиск отправляется с задержкой 300 мс после ввода.
- «Показать ещё» подгружает следующую страницу по курсору.
- Пустой результат: «Ничего не нашлось» и «Сбросить фильтры».
- «Сегодня» и «На неделе» включают «Предстоящие». При «Прошедших» они недоступны.

Макет: `filters-profile.html` (вне репозитория).

### 8.3 `/me` — мои регистрации

**Без сессии участника** — форма входа на этой же странице:
- email → «Получить код» → поле кода с таймером повтора (как S2-Code, D-025) → после кода профиль;
- `/me?next=<путь>`: после кода возврат на `next`, если это относительный путь приложения (начинается с одного `/`), иначе на `/me`. Ссылка «Войти, чтобы регистрироваться без кода» на `/e/:id` ведёт на `/me?next=/e/:id` (агент);
- ошибки кода те же, что на `/e/:id`.

**С сессией** — заголовок «Мои регистрации» и две вкладки:
- **«Текущие»** — событие не началось и регистрация не отменена. По возрастанию `starts_at`.
- **«Прошедшие»** — событие началось или регистрация отменена. По убыванию `starts_at` (агент).

Строка: название, дата и время, город или «Онлайн», статус, «Открыть» → `/r/:token`.

Статусы (агент):

| Состояние | Текст |
|---|---|
| `confirmed`, до начала | «Место ваше · билет XXXX-XXXX» |
| `waitlisted`, до начала | «Лист ожидания · №N» |
| `confirmed` с `checked_in_at` | «Пришли» |
| `confirmed` после начала без чекина | «Не отмечены на входе» |
| `waitlisted` после начала | «Место не освободилось» (D-034) |
| `cancelled` | «Отменена» |

Пустое состояние: «Вы пока никуда не зарегистрированы» и ссылка на каталог.

### 8.4 `/e/:id` — страница события

- Добавляются формат, город и адрес (у офлайн), категория, возраст по шкале.
- Если участник вошёл: email в форме показан текстом и не редактируется, имя и дата рождения предзаполнены из `lastData`, кнопка «Зарегистрироваться» вызывает `POST /events/:id/registrations`. Шага с кодом нет. Результат показывает существующий S3-Result.
- Если у участника уже есть регистрация: вместо формы «Вы уже зарегистрированы» и ссылка на `/r/:token`.
- Для гостя всё как сейчас.

### 8.5 `/organizer/events/new` и `…/edit`

Новые поля:
- «Формат» — две радиокнопки;
- «Город» и «Адрес» — видны и обязательны только при «Офлайн»;
- «Категория» — `<select>`;
- «Возрастное ограничение» — `<select>` 0+ / 6+ / 12+ / 16+ / 18+ вместо числового поля.

### 8.6 `/login`

Перестаёт быть главной, `/` больше не перенаправляет на `/organizer`. В шапке экрана входа есть ссылка на каталог (агент).

## 9. Письма

- Новый тип `login_code`: «Код для входа: NNNNNN», 10 минут. Шаблон — как у `code` (D-013).
- В письмах `confirmed`, `promoted`, `reminder` и `rescheduled` у офлайн-события добавляется строка с городом и адресом, у онлайн — «Онлайн» (агент).

## 10. Сид

Каждое из пяти событий получает формат, город, адрес и категорию. Например: «Митап» — `meetup`, онлайн; «Воркшоп» — `workshop`, Новосибирск; «Конференция» — `conference`, Новосибирск; «Ночной квиз» — `game`, Москва, 18+; «Лекция» — `lecture`, Новосибирск. Хотя бы два города нужны, чтобы фильтр было видно. README: таблица событий, «Что проверить руками» — пункты «каталог и фильтры» и «вход участника и профиль».

## 11. Тесты

Точки тестирования те же (D-041): тестовая сборка приложения и Playwright.

**Интеграционные (`app.request`):**
- каталог: каждый фильтр отдельно и в сочетании; `q` с `%`; `today` и `week` на границе дня в поясе `tz`; курсор без дублей и пропусков; `past` по убыванию; в ответе нет email и имён;
- `cities`: регистр и пробелы схлопываются;
- вход участника: код на email без регистраций уходит; минутный лимит; 5 попыток; cookie; `/participant/registrations` отдаёт только свой email, включая отменённые; сессия участника на `/organizer/*` → `401`;
- регистрация без кода: `confirmed`, `waitlisted`, `existing`, `below_min_age`, `registration_closed`, без сессии `401`; гонка за последнее место параллельно с обычной регистрацией по коду (как R3);
- событие: check `format`/`city`/`address`; `minAge` вне шкалы → `400`; миграция `min_age` округляет вверх.

**E2e (один новый сценарий):** гость на `/` фильтрует по городу → открывает событие → «Мои регистрации» → код из Mailpit → регистрация без кода → в `/me` во «Текущих» есть это событие со статусом «Место ваше».
