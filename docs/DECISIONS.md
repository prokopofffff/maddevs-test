## D-002 — Инфраструктура: свой бэкенд вместо Supabase (2026-10-19 17:20 +0700)
- Контекст: рассматривали Supabase как готовые Postgres + realtime + почту.
- Выбрали: свой бэкенд на Node + PostgreSQL + Mailpit (SMTP-заглушка с веб-UI), всё поднимается через `docker compose`.
- Альтернативы: Supabase — встроенный SMTP только для auth-писем (лимит ~2 письма/час, доставка только адресам команды проекта), то есть для билетов/напоминаний всё равно нужен свой SMTP; типичная схема «фронт → PostgREST + RLS» убирает Node-бэкенд, что конфликтует с требованием «Backend: Node.js», и уводит критичную логику (гонка за место, повышение из листа ожидания) в SQL-функции; облако требует аккаунт и ключи, локальный `supabase start` — ~10 контейнеров.
- Последствия: live-обновления (SSE/WS + `LISTEN/NOTIFY`) и отправку почты пишем сами; Mailpit даёт наблюдаемые письма для проверки и тестов.

- Последствия: предусловия — Node 22, pnpm (через corepack), Docker.

## D-004 — HTTP-фреймворк: Hono на Node (2026-10-19 17:20 +0700)
- Контекст: выбор между Hono, Fastify, Express 5.
- Выбрали: Hono через `@hono/node-server`.
- Альтернативы: Fastify — зрелый продакшн-стандарт, но больше церемоний и нет типизированного клиента; Express 5 — слабые типы, валидацию/SSE собирать вручную.
- Последствия: встроенный `streamSSE`, `@hono/zod-validator`, тесты через `app.request()` без поднятия сервера, типизированный RPC-клиент `hc` во фронте (общие типы API). Экосистема под Node меньше, чем у Fastify/Express.

## D-005 — Вход организатора: email + пароль, сессия в cookie (2026-10-19 21:52 +0700)
- Контекст: тикет «Модель входа организатора» (#4). Организаторов много, у каждого свои события; участник аккаунта не имеет.
- Выбрали: открытая регистрация организатора по email + паролю; хеш через `scrypt` из `node:crypto`; email обрезается и приводится к нижнему регистру, уникален в БД; пароль — минимум 8 символов, без правил состава. Сессия — opaque id в httpOnly cookie (`SameSite=Lax`, 30 дней), таблица `sessions` в Postgres; «Выйти» удаляет сессию и cookie. Отдельного CSRF-токена нет: API только JSON, `SameSite=Lax`, фронт и API на одном origin. Ошибка входа одна на неверный email и неверный пароль. Сид: `demo@example.com` / `demo` с готовым событием и регистрациями (хеш пишется в обход валидации). Организатор видит и меняет только свои события, на чужие — `404`. Экран чекина — только под сессией владельца события.
- Альтернативы: magic link через Mailpit — ревьюеру и e2e пришлось бы ходить в Mailpit на каждый вход, и письму входа нужен путь мимо outbox; секретная admin-ссылка на событие — нет «моих событий», потерянная ссылка = потерянное событие; JWT — секрет, refresh, нет отзыва, а `EventSource` не шлёт заголовок `Authorization`; отдельная ссылка чекина для волонтёра — лишняя модель доступа.
- Последствия: сброс пароля, «выйти на всех устройствах», роль волонтёра на входе — вне рамок. SSE-поток счётчика авторизуется той же cookie.

## D-006 — Rate limit на все запросы (2026-10-19 21:52 +0700)
- Контекст: тикет «Модель входа организатора» (#4); защиту от перебора решили не выносить за рамки, а ограничить частоту всех запросов.
- Выбрали: `hono-rate-limiter` 0.5.x с хранилищем в памяти процесса. Три корзины по IP, значения из env: общая — 300/мин на все маршруты; вход и регистрация организатора — 10/мин; публичные действия участника (регистрация на событие, отказ) — 20/мин. Чекин и экран организатора — под общей. IP — адрес сокета через `getConnInfo`; `X-Forwarded-For` только при `TRUST_PROXY=1`. Подключение SSE — один запрос, переподключения считаются. Превышение — `429`, `Retry-After`, заголовки `RateLimit-*`, тело `{ error: "rate_limited" }`; фронт показывает «Слишком много запросов, попробуйте через N секунд». В тестах и e2e лимиты подняты через env; отдельный тест: 11-я попытка входа за минуту → `429`.
- Альтернативы: счётчики в Postgres — лишняя запись на каждый запрос; Redis — ещё один контейнер; блокировка аккаунта после N неудач — даёт заблокировать чужой аккаунт.
- Последствия: счётчики сбрасываются при рестарте и не работают при нескольких процессах — честно пишем в README. Если фронт проксирует API (Vite/nginx), все запросы приходят с одного IP — тикет «Фронтенд: сборка, роутинг, работа с данными» обязан включить `TRUST_PROXY`.

## D-007 — Участник без аккаунта: код подтверждения, отказ по личной ссылке, повторная регистрация (2026-10-20 09:44 +0700)
- Контекст: тикет «Отказ и повторная регистрация участника без аккаунта» (#5). Участник идентифицируется только email; нужно доказать право на отказ и не создавать второго места при повторной регистрации.
- Выбрали: владение email подтверждается **кодом в форме регистрации**, без аккаунта: форма → письмо с кодом (6 цифр, 10 минут, 5 попыток, повторная отправка не чаще раза в минуту) → после верного кода — распределение места. Место на время ввода кода не держится. После кода экран показывает результат («Место ваше» / «№N в листе ожидания»), письмо с билетом и личной ссылкой уходит в обоих случаях. Отказ — по личной ссылке из письма (случайный токен, не код билета): GET открывает страницу регистрации, отказ — POST кнопкой (почтовые сканеры открывают ссылки сами); отказ возможен и из листа ожидания (без повышения); после отказа — письмо-подтверждение. Потерял письмо — email + код на странице события ведут на ту же страницу регистрации. Повторная регистрация при активной (подтверждена или в листе ожидания) — после кода показываем существующую, второго места нет, позиция сохраняется, новые данные не применяются. После отказа — новая регистрация по общим правилам, старые билет и ссылка мертвы; инвариант — не больше одной неотменённой регистрации на (событие, email). Email: trim + lower-case, как у организатора (D-005). Отправка кода и отказ — в корзине «публичные действия участника» (D-006).
- Альтернативы: место сразу без подтверждения + «исправить адрес» в течение 30 минут из того же браузера — сначала выбрали, затем заменили: остаются места, занятые чужими/выдуманными адресами, и сложная логика исправления (только своя регистрация, слияние с существующей); double opt-in с бронью до клика — состояние «ожидает подтверждения» со сроком усложняет гонку и лист ожидания; аккаунт участника со входом по коду — «мои регистрации» нет в требованиях, меняет язык домена, +день работы; отказ по коду билета — код видит человек на входе, у листа ожидания билета нет.
- Последствия: письмо с кодом должно доходить за секунды — требование к тикету «Отправка писем»; e2e берёт код из Mailpit API; на демо ревьюеру нужно открыть Mailpit, чтобы зарегистрироваться (то же трение, из-за которого вход организатора — пароль, D-005), — пишем в README.

## D-008 — Данные участника и минимальный возраст события (2026-10-20 09:44 +0700)
- Контекст: тот же тикет; пользователь предложил собирать имя, фамилию и возраст и использовать возраст для ограничений событий.
- Выбрали: участник указывает имя, фамилию, дату рождения; у события необязательный минимальный возраст, возраст считается на день события; младше — отказ до отправки кода. Дата рождения — самодекларация; экран чекина показывает имя и дату рождения для сверки с документом. Участник свои данные не правит — только через поддержку (отдельный тикет «Поддержка: роль и правка данных участника», #18).
- Альтернативы: число полных лет — устаревает и даёт ложный отказ тому, кому исполнится нужный возраст до события; только email — организатор не видит, кто пришёл, и нет возрастных ограничений; правка участником самим — без аккаунта нечем подтвердить, что правит он, и открывает подмену данных после проверки возраста.
- Последствия: храним персональные данные (дату рождения) — минимум полей, без документов. Открыто: изменение минимального возраста или перенос события после регистраций — в тумане карты.

## D-009 — Доступ к БД: Drizzle на postgres.js, миграции drizzle-kit (2026-10-20 10:01 +0700)
- Контекст: тикет «Доступ к БД и миграции» (#7). Критичное поведение (гонка за место, повышение, одно напоминание, один чекин) держится на транзакциях и блокировках; основа — «Обзор: доступ к PostgreSQL из Node» (#6).
- Выбрали: `drizzle-orm@0.45` поверх `postgres@3.4` (postgres.js), миграции — `drizzle-kit@0.31`: `generate` пишет SQL-файлы в репо, применяются программно (`migrate(db)`) при старте API до `listen`. Версии запиннены, 1.0 RC не берём; `drizzle-kit push` не используем. Ретраи на `40001`/`40P01` — своя обёртка. `LISTEN/NOTIFY`, если понадобится, — через `db.$client.listen`, без второго драйвера.
- Альтернативы: Kysely — равноценен по транзакциям и блокировкам, но миграции руками и типы БД через codegen, `LISTEN` на отдельном `pg.Client` — запасной вариант; Prisma — `FOR UPDATE` только raw SQL, `latest` указывает на 8.0 RC без уровней изоляции; голый postgres.js — типы и миграции вручную; `node-pg-migrate` — не нужен, раз миграции генерирует drizzle-kit.
- Последствия: одна TS-схема даёт и типы, и миграции. Применение миграций при старте рассчитано на один процесс API (как и rate limit, D-006); при нескольких репликах нужен отдельный шаг миграции. SQL от `.for()` проверяем первым интеграционным тестом — метод описан только в типах пакета.

## D-010 — Демо-данные: отдельная команда, набор сценариев (2026-10-20 10:01 +0700)
- Контекст: тот же тикет; ревьюер должен проверить требования, не создавая данные руками; вход демо-организатора уже задан в D-005.
- Выбрали: сид — отдельная команда `pnpm db:seed` (в compose: `docker compose exec api pnpm db:seed`), шаг описан в README; на непустой базе отказывается и подсказывает `pnpm db:reset` (стереть, применить миграции, засеять). Даты считаются от момента запуска сида. Регистрации пишутся прямо в БД: без кода подтверждения и без писем. Набор: `demo@example.com` / `demo` с событиями — заполненное с листом ожидания; начинается завтра (для напоминания); прошедшее с чекинами; с минимальным возрастом; второй организатор `demo2@example.com` / `demo` со своим событием (проверка изоляции, `404` на чужое). Тесты сид не используют.
- Альтернативы: сид автоматически при первом старте — меньше шагов для ревьюера, но пользователь выбрал явную команду: база после `up` честно пустая, сид — осознанное действие; без демо-данных — ревьюер собирает лист ожидания, чекин и напоминание вручную; минимальный сид (одно событие) — дешевле, но те же ручные шаги.
- Последствия: README обязан содержать команду сида сразу после `docker compose up`. Сид меняется вместе со схемой — держим его маленьким. Событие «завтра» после сида попадает под ближайший sweep напоминаний — письма появятся в Mailpit.
