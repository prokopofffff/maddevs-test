## D-005 — Вход организатора: email + пароль, сессия в cookie (2026-10-19 21:52 +0700)
- Контекст: тикет «Модель входа организатора» (#4). Организаторов много, у каждого свои события; участник аккаунта не имеет.
- Выбрали: открытая регистрация организатора по email + паролю; хеш через `scrypt` из `node:crypto`; email обрезается и приводится к нижнему регистру, уникален в БД; пароль — минимум 8 символов, без правил состава. Сессия — opaque id в httpOnly cookie (`SameSite=Lax`, 30 дней), таблица `sessions` в Postgres; «Выйти» удаляет сессию и cookie. Отдельного CSRF-токена нет: API только JSON, `SameSite=Lax`, фронт и API на одном origin. Ошибка входа одна на неверный email и неверный пароль. Сид: `demo@example.com` / `demo` с готовым событием и регистрациями (хеш пишется в обход валидации). Организатор видит и меняет только свои события, на чужие — `404`. Экран чекина — только под сессией владельца события.
- Альтернативы: magic link через Mailpit — ревьюеру и e2e пришлось бы ходить в Mailpit на каждый вход, и письму входа нужен путь мимо outbox; секретная admin-ссылка на событие — нет «моих событий», потерянная ссылка = потерянное событие; JWT — секрет, refresh, нет отзыва, а `EventSource` не шлёт заголовок `Authorization`; отдельная ссылка чекина для волонтёра — лишняя модель доступа.
- Последствия: сброс пароля, «выйти на всех устройствах», роль волонтёра на входе — вне рамок. SSE-поток счётчика авторизуется той же cookie.

## D-006 — Rate limit на все запросы (2026-10-19 21:52 +0700)
- Контекст: тикет «Модель входа организатора» (#4); защиту от перебора решили не выносить за рамки, а ограничить частоту всех запросов.
- Выбрали: `hono-rate-limiter` 0.5.x с хранилищем в памяти процесса. Три корзины по IP, значения из env: общая — 300/мин на все маршруты; вход и регистрация организатора — 10/мин; публичные действия участника (регистрация на событие, отказ) — 20/мин. Чекин и экран организатора — под общей. IP — адрес сокета через `getConnInfo`; `X-Forwarded-For` только при `TRUST_PROXY=1`. Подключение SSE — один запрос, переподключения считаются. Превышение — `429`, `Retry-After`, заголовки `RateLimit-*`, тело `{ error: "rate_limited" }`; фронт показывает «Слишком много запросов, попробуйте через N секунд». В тестах и e2e лимиты подняты через env; отдельный тест: 11-я попытка входа за минуту → `429`.
- Альтернативы: счётчики в Postgres — лишняя запись на каждый запрос; Redis — ещё один контейнер; блокировка аккаунта после N неудач — даёт заблокировать чужой аккаунт.
- Последствия: счётчики сбрасываются при рестарте и не работают при нескольких процессах — честно пишем в README. Если фронт проксирует API (Vite/nginx), все запросы приходят с одного IP — тикет «Фронтенд: сборка, роутинг, работа с данными» обязан включить `TRUST_PROXY`.

## D-007 — Участник без аккаунта: код подтверждения, отказ по личной ссылке, повторная регистрация (2026-10-20 09:44 +0700)
- Контекст: тикет «Отказ и повторная регистрация участника без аккаунта» (#5). Участник идентифицируется только email; нужно доказать право на отказ и не создавать второго места при повторной регистрации.
- Выбрали: владение email подтверждается **кодом в форме регистрации**, без аккаунта: форма → письмо с кодом (6 цифр, 10 минут, 5 попыток, повторная отправка не чаще раза в минуту) → после верного кода — распределение места. Место на время ввода кода не держится. После кода экран показывает результат («Место ваше» / «№N в листе ожидания»), письмо с билетом и личной ссылкой уходит в обоих случаях. Отказ — по личной ссылке из письма (случайный токен, не код билета): GET открывает страницу регистрации, отказ — POST кнопкой (почтовые сканеры открывают ссылки сами); отказ возможен и из листа ожидания (без повышения); после отказа — письмо-подтверждение. Потерял письмо — email + код на странице события ведут на ту же страницу регистрации. Повторная регистрация при активной (подтверждена или в листе ожидания) — после кода показываем существующую, второго места нет, позиция сохраняется, новые данные не применяются. После отказа — новая регистрация по общим правилам, старые билет и ссылка мертвы; инвариант — не больше одной неотменённой регистрации на (событие, email). Email: trim + lower-case, как у организатора (D-005). Отправка кода и отказ — в корзине «публичные действия участника» (D-006).
- Альтернативы: место сразу без подтверждения + «исправить адрес» в течение 30 минут из того же браузера — сначала выбрали, затем заменили: остаются места, занятые чужими/выдуманными адресами, и сложная логика исправления (только своя регистрация, слияние с существующей); double opt-in с бронью до клика — состояние «ожидает подтверждения» со сроком усложняет гонку и лист ожидания; аккаунт участника со входом по коду — «мои регистрации» нет в требованиях, меняет язык домена, +день работы; отказ по коду билета — код видит человек на входе, у листа ожидания билета нет.
- Последствия: письмо с кодом должно доходить за секунды — требование к тикету «Отправка писем»; e2e берёт код из Mailpit API; на демо ревьюеру нужно открыть Mailpit, чтобы зарегистрироваться (то же трение, из-за которого вход организатора — пароль, D-005), — пишем в README.

## D-011 — Гонка за последнее место: блокировка строки события (2026-10-20 10:10 +0700)
- Контекст: тикет «Распределение мест: гонка за последнее место и повышение из листа ожидания» (#8). Два человека одновременно подтверждают код на последнее место — место получает ровно один, второй попадает в лист ожидания.
- Выбрали: каждая операция, меняющая занятость мест (распределение после кода подтверждения, отказ, изменение лимита мест), — одна транзакция на уровне READ COMMITTED, которая первым шагом берёт `SELECT … FROM events WHERE id = $1 FOR UPDATE`. Под блокировкой: есть неотменённая регистрация этого email — возвращаем её (D-007); иначе `count(*)` подтверждённых < лимита → регистрация «подтверждена» с билетом, иначе «в листе ожидания». Счётчики не храним: число подтверждённых и ожидающих считается запросом по индексу `(event_id, status)`. Частичный уникальный индекс `(event_id, email) WHERE status <> 'cancelled'` — страховка инварианта «одна неотменённая регистрация». Порядок блокировок всегда «событие → регистрации»; на `40P01` — ретрай обёрткой из D-009. Чекин и перенос места не меняют и строку события не блокируют.
- Альтернативы: колонка-счётчик с условным `UPDATE … WHERE confirmed < limit` — та же блокировка строки, но второй источник правды, который надо синхронизировать при отказе, повышении и смене лимита; SERIALIZABLE + ретраи — корректно, но ошибки сериализации на каждой гонке, ретраи с повторной логикой и ложные конфликты, рассуждать о коде сложнее; `pg_advisory_xact_lock(event_id)` — тот же эффект, что блокировка строки, но вне модели данных, ключи без пространства имён, забытый вызов не виден в SQL.
- Последствия: все изменения мест одного события выполняются последовательно — для стенда (и для событий на тысячи мест) это не узкое место; разные события не мешают друг другу. Доказательство — интеграционный тест на реальном Postgres: N параллельных соединений на событие с одним свободным местом → ровно одна подтверждённая, остальные в листе ожидания с позициями 1…N−1 (тикет «Доказуемость: тесты, e2e на две вкладки, CI», #16).

## D-012 — Повышение из листа ожидания: в той же транзакции, до начала события (2026-10-20 10:10 +0700)
- Контекст: тот же тикет; «кто-то отказался — первый из листа автоматически получает место и письмо».
- Выбрали: повышение выполняется в транзакции отказа под той же блокировкой события (D-011): отменяем регистрацию; если она была подтверждённой — первая в листе ожидания (по времени подтверждения кода, затем id) становится подтверждённой и получает билет. Та же функция «заполнить свободные места» вызывается при увеличении лимита мест — новые места забирает лист ожидания по порядку. Инвариант: свободное место и непустой лист ожидания одновременно не существуют. Письма (билет повышенному, «вы отказались» отказавшемуся) ставятся в outbox `INSERT`-ом в той же транзакции — откат отказа не оставляет писем, коммит не теряет их; доставка — тикет «Отправка писем: заглушка и гарантии доставки» (#9). Позиция в листе — время подтверждения кода (место на время ввода кода не держится, D-007); повторная регистрация после отказа встаёт в конец. Повышение работает вплоть до начала события, без отсечки.
- Альтернативы: остановить повышения за N часов до начала — место пустует, нарушается инвариант, нужен отдельный случай в тестах, а требование говорит «автоматически»; повышение отдельной фоновой задачей после отказа — окно, в котором место свободно и его забирает новая регистрация в обход листа, плюс ещё одна точка отказа; предложение места с подтверждением в течение N часов — состояние «предложено» со сроком, не просили.
- Последствия: место, освободившееся за минуты до начала, достаётся человеку, который может не успеть прочитать письмо и не прийти. Будут ли отказ и повышение открыты после начала события — открытый вопрос карты. Уменьшение лимита ниже числа подтверждённых тоже остаётся в тумане; механизм блокировки для него тот же.

## D-013 — Доставка писем: outbox в той же транзакции, свой цикл отправки, at-least-once (2026-10-20 10:21 +0700)
- Контекст: тикет «Отправка писем: заглушка и гарантии доставки» (#9). Письма (код подтверждения, «место ваше» с билетом, «вы в листе ожидания», повышение с билетом, «вы отказались», напоминание, перенос) не должны теряться при падении процесса и не должны уходить при откате действия (D-012). Опора — «Обзор: раннеры фоновых задач на Postgres для Node» (#10).
- Выбрали: таблица `email_outbox` — `id`, `dedup_key text unique`, `kind`, `to_email`, `subject`, `text`, `html`, `created_at`, `attempts`, `next_attempt_at`, `locked_until`, `sent_at`, `failed_at`, `last_error`; частичный индекс `WHERE sent_at IS NULL AND failed_at IS NULL`. Постановка — `INSERT … ON CONFLICT (dedup_key) DO NOTHING` в транзакции самого действия; письмо рендерится в этот момент (снимок: письмо сообщает о факте на момент действия, следующее письмо его поправляет). Ключи: `code:<id кода>`, `confirmed:<registration_id>`, `waitlisted:<registration_id>`, `promoted:<registration_id>`, `cancelled:<registration_id>`, `reminder:<registration_id>`; ключ письма о переносе и повторное напоминание после переноса — в «Время события и семантика переноса» (#11) и «Ровно одно напоминание за сутки» (#12). Отправка — свой цикл в процессе API, без библиотеки: `dispatchOutbox(now)` каждые 2 с и сразу после коммита транзакции, поставившей письмо (D-014); захват пачки до 20 строк по `id` через `FOR UPDATE SKIP LOCKED` с арендой `locked_until = now + 2 мин`, транзакция на время SMTP не держится. SMTP — nodemailer → Mailpit; письмо multipart: HTML + текстовая версия, шаблоны — функции на TypeScript без шаблонизатора; `Message-ID` выводится из `id` строки outbox, повтор уходит с тем же. Успех — `sent_at`; ошибка — `attempts + 1`, `next_attempt_at = now + 30 с · 2^(attempts−1)` (потолок 1 ч), `last_error`; после 10 попыток — `failed_at` и запись в лог, в интерфейсе не показываем. Время — параметр функции, тесты без таймеров. Гарантия — **at-least-once**: письмо, поставленное закоммиченной транзакцией, не теряется (аренда истекает, строку забирает следующий проход); дубль возможен только при падении между «SMTP принял» и коммитом `sent_at` (выбор пользователя). «Ровно одно напоминание» держится на постановке: второй строки с тем же ключом не бывает; узкое окно дубля при падении описываем в README.
- Альтернативы: отправка прямо из запроса — письмо теряется при падении после коммита и уходит при откате, если отправлено до коммита; at-most-once (отметить «отправляется» до SMTP) — при падении письмо пропадает, а потерянный билет хуже дубля; at-most-once только для напоминаний — два режима в одной таблице ради случая, который на стенде не воспроизводится; pg-boss / graphile-worker — обе at-least-once, ключ и `sent_at` всё равно нужны, плюс чужая схема (#10); отдельный процесс-воркер — второй контейнер и LISTEN/NOTIFY для мгновенного пинка, а `SKIP LOCKED` и так делает второй экземпляр безопасным; рендер при отправке из текущих данных — письмо о повышении могло бы описывать уже отменённую регистрацию, нужна логика «устарело ли письмо».
- Последствия: письмо уходит не раньше коммита действия; порядок писем одному адресату не строгий только при повторах после ошибки SMTP (на стенде не бывает). Неотправленные после 10 попыток видны только в логе и таблице. Тесты: `dispatchOutbox(now)` с фейковым транспортом — успех, ошибка с backoff, истёкшая аренда забирается повторно, `failed_at` после 10 попыток; e2e читает письма из Mailpit API.

## D-014 — Письмо с кодом подтверждения: та же очередь, немедленный пинок (2026-10-20 10:21 +0700)
- Контекст: тот же тикет; участник ждёт код на экране, письмо должно прийти за секунды (D-007).
- Выбрали: код ставится в outbox как любое письмо; после коммита обработчик запроса вызывает `outbox.wake()` — отправка стартует сразу, не дожидаясь 2-секундного тика. Экран после отправки формы говорит «код отправлен»; «отправить ещё раз» — не чаще раза в минуту (D-007), каждая повторная отправка — новый код и новая строка outbox.
- Альтернативы: синхронная отправка из запроса — при упавшей почте участник сразу видит ошибку, но это второй путь отправки со своей логикой ошибок, ответ формы зависит от SMTP, а при таймауте код в базе есть, а письма нет.
- Последствия: если почта недоступна, участник узнаёт об этом не сразу — письмо придёт после восстановления (повторами D-013) или он запросит код заново; код живёт 10 минут, так что письмо, пришедшее позже, может быть уже бесполезным. Пинок работает внутри одного процесса; при нескольких экземплярах API код ушёл бы по общему 2-секундному тику.

## D-015 — Время события: момент начала и часовой пояс события (2026-10-20 10:33 +0700)
- Контекст: тикет «Время события и семантика переноса» (#11). Время события видят организатор, участник на странице события и в письмах; «за сутки до начала» считается от него.
- Выбрали: `events.starts_at timestamptz` + `events.timezone text` (IANA, например `Asia/Novosibirsk`). При создании пояс по умолчанию — пояс браузера организатора (`Intl.DateTimeFormat().resolvedOptions().timeZone`), в форме его можно сменить. Организатор вводит дату и время в поясе события, сервер переводит их в момент. Везде — кабинет организатора, страница события, билет, письма — время показывается в поясе события с подписью смещения: «25 октября 2026, 19:00 (UTC+7)». Форматирование — `Intl.DateTimeFormat('ru-RU', { timeZone })`; перевод введённого локального времени в момент — `@date-fns/tz` (`TZDate`), потому что в Node 22 нет Temporal (рутинный выбор, можно заменить при реализации). Конец события не храним — только начало. Решено агентом как стандартная практика (Eventbrite и Meetup показывают очные события во времени места проведения).
- Альтернативы: пояс браузера зрителя — в письме его не узнать, а участник из другого пояса увидит время не там, где проходит событие; только UTC — неудобно всем; локальное время без пояса — нельзя посчитать «за сутки до» и сравнить с текущим моментом.
- Последствия: введённое время, попадающее в переход на летнее время (несуществующий или двойной час), разрешается правилом библиотеки по умолчанию — для стенда достаточно. Смена только пояса при том же моменте — не перенос (D-016).

## D-016 — Перенос: письмо всем неотменённым, напоминание заново, если до новой даты больше суток (2026-10-20 10:33 +0700)
- Контекст: тот же тикет; «организатор перенёс событие — все участники получают письмо» и «напоминание за сутки, ровно одно». Условие из D-013: ключ письма о переносе должен различать переносы.
- Выбрали: перенос — изменение момента начала (`starts_at`); правка описания, лимита мест или только пояса при том же моменте переносом не является, писем нет. Перенести можно только ещё не начавшееся событие и только на будущий момент. Транзакция переноса первым шагом берёт `SELECT … FROM events WHERE id = $1 FOR UPDATE` (уточнение к D-011: иначе регистрация, конкурирующая с переносом, получила бы письмо со старым временем и не получила письма о переносе), увеличивает `reschedule_count` и для каждой неотменённой регистрации — подтверждённой и в листе ожидания — ставит в outbox письмо с ключом `rescheduled:<registration_id>:<reschedule_count>`: старое и новое время в поясе события и статус регистрации. Каждый перенос — своё письмо, без склейки. Напоминание (выбор пользователя): одно на каждое время начала, а не одно навсегда. Если новое начало дальше суток от момента переноса, напоминание «взводится» заново и придёт за сутки до новой даты; если ближе суток, второго напоминания нет — его роль играет письмо о переносе, в том числе когда напоминание к старой дате ещё не уходило. Механизм (ключ напоминания с номером «раунда», как сторож видит раунд, закрытый письмом о переносе) — в «Ровно одно напоминание за сутки» (#12).
- Альтернативы: одно напоминание навсегда — буквально «ровно одно», но после переноса на неделю участник остаётся без напоминания о реальной дате; новое напоминание на каждое время начала без условия — при сдвиге на час второе напоминание приходит сразу вслед за письмом о переносе; письмо о переносе только подтверждённым — требование говорит «все участники», а по глоссарию участник из листа ожидания тоже участник и может получить место.
- Последствия: «ровно одно» в README формулируется как «ровно одно на каждое время начала; перенос внутрь суток заменяет напоминание» и подтверждается тестом (#16). Частые переносы подряд дают по письму на каждый. Событие, созданное или с регистрацией меньше чем за сутки до начала, — открытый вопрос карты.

## D-017 — Возраст после переноса или повышения минимального возраста: регистрация остаётся (2026-10-20 10:33 +0700)
- Контекст: тот же тикет и пункт тумана карты. Минимальный возраст проверяется на день события (D-008); перенос на более раннюю дату или повышение минимального возраста может сделать часть регистраций неподходящими.
- Выбрали (выбор пользователя): возраст проверяется только при регистрации. Сохранение переноса или повышения минимального возраста не блокируется и ничего не отменяет; сервер в ответе возвращает число неотменённых регистраций, не проходящих по новым условиям, и форма организатора показывает предупреждение «2 участника не проходят по возрасту на новую дату». Повышение из листа ожидания возраст не перепроверяет.
- Альтернативы: автоматическая отмена с письмом и повышением следующего — отнимает билет у человека из-за правки организатора; запрет сохранения, пока такие регистрации есть, — блокирует законный перенос из-за одного человека, а отменить чужую регистрацию организатор не может.
- Последствия: на вход может прийти владелец билета, не проходящий по возрасту, — решается на входе или через поддержку («Поддержка: роль и правка данных участника», #18).

## D-018 — Напоминание: ежеминутный проход в outbox, ключ по номеру переноса, время параметром (2026-10-20 10:40 +0700)
- Контекст: тикет «Ровно одно напоминание за сутки» (#12). Каждая подтверждённая регистрация получает одно напоминание на каждое время начала (D-016), переживая рестарт сервера, перенос и повышение из листа ожидания после рассылки. Тест не должен ждать сутки. Опора — «Обзор: раннеры фоновых задач» (#10) и outbox (D-013).
- Выбрали: функция `sweepReminders(now)` в процессе API, таймер раз в минуту; `now` — параметр, в SQL только `$now`, никакого `now()`. Проход — одна транзакция: сначала `SELECT id FROM events WHERE starts_at > $now AND starts_at <= $now + interval '24 hours' FOR SHARE` (условие перепроверяется на свежей версии строки), затем отдельным оператором `INSERT INTO email_outbox … SELECT … ON CONFLICT (dedup_key) DO NOTHING` по этим событиям для регистраций со статусом «подтверждена» и `GREATEST(r.confirmed_at, e.rescheduled_at) < e.starts_at - interval '24 hours'`. Ключ — `reminder:<registration_id>:<reschedule_count>` (номер переноса из D-016 служит номером «раунда», отдельного счётчика нет). Блокировка `FOR SHARE` конфликтует с `FOR UPDATE`, которую берут регистрация, отказ с повышением и перенос (D-011, D-016): пока проход ставит напоминания, ни одно из этих действий над теми же событиями не идёт, а второй оператор в READ COMMITTED берёт новый снимок и видит их результат целиком. Новые поля: `registrations.confirmed_at` (момент перехода в «подтверждена» — при подтверждении email или при повышении), `events.rescheduled_at` (момент последнего переноса, `NULL`, если переносов не было). Одно условие покрывает все случаи: перенос дальше суток — новый ключ и новое напоминание за сутки до новой даты; перенос внутрь суток — `rescheduled_at` внутри последних суток, напоминания нет, его заменяет письмо о переносе (D-016); подтверждение или повышение внутри последних суток — напоминания нет (D-019). Рестарт: состояния в памяти нет, пропущенное за простой уходит первым проходом после старта, пока событие не началось (как `missed: 'once'` у pg-boss, #10). Два экземпляра или два параллельных прохода безопасны: `ON CONFLICT` оставляет одну строку. «За сутки» — ровно 24 часа до момента начала; письмо приходит в пределах минуты после этой отметки. Письмо рендерится при постановке (снимок, D-013): название, время в поясе события (D-015), код билета и личная ссылка. Решено агентом как стандартная практика; спрошен только вопрос D-019.
- Альтернативы: отложенная задача на каждую регистрацию (pg-boss `startAfter`, graphile-worker `run_at`) — перенос и повышение требуют перепланирования с гонками у уже выполняющейся задачи (#10); флаг «раунд закрыт» на событии вместо сравнения с `rescheduled_at` — лишнее поле и отдельная ветка в переносе, а случай поздней регистрации всё равно требует `confirmed_at`; проход без блокировки событий — перенос внутрь суток, закоммиченный посреди прохода, пропустил бы напоминание со старым временем следом за письмом о переносе; удаление неотправленных напоминаний в транзакции переноса или отказа — строка может быть уже взята циклом отправки, а снимок письма и так поправляется следующим письмом (D-013); управляемые часы в рантайме (`CLOCK_OFFSET`) для демонстрации — хватает демо-сида (D-010).
- Последствия: «ровно одно на каждое время начала» держится на уникальном ключе постановки; доставка — at-least-once с окном дубля при падении в момент отправки (D-013), это окно описываем в README. Если отказ или перенос происходит в те секунды, когда напоминание уже поставлено, но ещё не отправлено, участник получит напоминание-снимок, а за ним письмо об отказе или переносе. Проход ненадолго ждёт идущие транзакции регистрации по событиям последних суток. Демо-сид (D-010) создаёт событие с началом меньше чем через сутки и регистрации с `confirmed_at` больше чем за сутки до начала — иначе по D-019 напоминания не будет. Тесты на настоящем Postgres вызывают `sweepReminders(t)` с выбранными моментами, без таймеров и ожидания: за 25 ч — ноль; за 24 ч — одна строка; повторный проход — всё ещё одна; первый проход после «простоя» за 20 ч — одна; два параллельных прохода на разных соединениях — одна; лист ожидания и отменённые — ноль; после начала — ноль; перенос на неделю после отправки — вторая строка с новым ключом; перенос внутрь суток до отправки — ноль, есть письмо о переносе; повышение за 30 ч — напоминание за 24 ч; повышение или регистрация за 20 ч — ноль.

## D-019 — Позднее подтверждение: напоминания нет, его заменяет письмо «место ваше» (2026-10-20 10:40 +0700)
- Контекст: тот же тикет и пункт тумана карты «событие создано или участник зарегистрировался меньше чем за сутки до начала». То же касается повышения из листа ожидания, когда напоминания уже ушли.
- Выбрали (выбор пользователя): если регистрация стала подтверждённой меньше чем за сутки до начала — при подтверждении email или при повышении, — отдельного напоминания нет: письмо «место ваше» или письмо о повышении с билетом и временем приходит минуты назад и само служит напоминанием. Правило то же, что у переноса внутрь суток (D-016): любое письмо о событии в последние сутки заменяет напоминание. Событие, созданное меньше чем за сутки до начала, отдельного правила не требует — все его регистрации поздние.
- Альтернативы: напоминание сразу, через минуту после письма «место ваше», — два письма подряд с одним содержанием; напоминание только повышенным из листа ожидания — два правила вместо одного без выигрыша для участника.
- Последствия: в README «ровно одно напоминание» формулируется как «ровно одно на каждое время начала, если место получено больше чем за сутки; иначе его роль играет письмо о месте или о переносе». Письма «место ваше» и о повышении должны содержать время в поясе события и билет — они и так их содержат (D-013, D-015).

## D-020 — Live-счётчики: SSE, NOTIFY из триггера при коммите, полный снимок (2026-10-20 10:49 +0700)
- Контекст: тикет «Live-счётчик у организатора: SSE или WebSocket» (#13). «Счётчик пришедших у организатора обновляется live»; экран показывает подтверждённых, лист ожидания и пришедших (D-021). Счётчики не хранятся (D-011), изменения мест идут под блокировкой строки события, чекин её не берёт.
- Выбрали: транспорт — SSE через `streamSSE` из `hono/streaming` (D-004): `GET /api/organizer/events/:id/live` под сессией владельца, чужое событие — `404` (D-005); в браузере `EventSource` на том же origin, cookie уходит сам. Сервер шлёт `retry: 3000`, комментарий-пинг каждые 20 с, заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no`. Источник — Postgres `LISTEN/NOTIFY`: триггеры `AFTER INSERT OR UPDATE OR DELETE` на `registrations` (при смене статуса или отметки чекина) и `AFTER UPDATE OF` лимита мест на `events` вызывают `pg_notify('event_counts', event_id::text)`; уведомление доставляется только при коммите, откат не шлёт ничего, одинаковые уведомления одной транзакции Postgres склеивает. Триггеры — SQL-миграция drizzle-kit (`--custom`, D-009). В процессе API одно `sql.listen('event_counts', onnotify, onlisten)` из postgres.js (отдельное соединение, само переподключается) и карта «событие → открытые потоки». На уведомление по событию, у которого есть подписчики, — пересчёт одним запросом (`count(*) FILTER (…)` по индексу `(event_id, status)` + лимит) не чаще раза в 200 мс на событие, результат рассылается всем его потокам. Шлём полный снимок `event: counts`, `data: {confirmed, limit, waitlisted, checkedIn}`: сразу при подключении, после каждого изменения и всем подписчикам в `onlisten` после переподключения слушателя (уведомления за время разрыва потеряны, снимок их покрывает). `id` и `Last-Event-ID` не нужны: переподключившийся браузер сразу получает свежий снимок. Подключение считается одним запросом в rate limit (D-006). Решено агентом как стандартная практика; пользователю заданы только вопросы D-021.
- Альтернативы: WebSocket (`@hono/node-ws`) — двусторонний канал не нужен, переподключение и пинги пишутся руками, отдельный путь апгрейда мимо middleware; polling раз в 2–5 с — не live, и каждая открытая вкладка тратит общий лимит 300/мин (D-006); in-process `EventEmitter` после коммита — в каждом пути (регистрация, отказ с повышением, смена лимита, чекин) надо не забыть `emit` и сделать его строго после коммита, а изменения из другого процесса (`pnpm db:seed`, второй экземпляр, `psql` на демо) не видны; явный `pg_notify` в каждой транзакции вместо триггера — та же доставка при коммите, но забытый вызов в новом пути молча ломает live, а триггер ловит любое изменение строки, включая сид; счётчики в теле уведомления, посчитанные в транзакции, — лишний запрос в каждой записи, а чекины без блокировки события, закоммиченные в разном порядке, могли бы прислать устаревший снимок последним; дельты (`checkedIn +1`) — потерянное или повторное сообщение навсегда сдвигает цифру, снимок из четырёх чисел идемпотентен.
- Последствия: +1 соединение к Postgres на процесс под `LISTEN`; несколько экземпляров API работают без доработок — каждый слушает сам. Логика уведомлений живёт в схеме, а не в TypeScript: в README и рядом с миграцией пишем, откуда берутся события. Задержка обновления — коммит + до 200 мс + запрос. Если API проксируется (тикет «Фронтенд», #15), прокси не должен буферизовать и сжимать `text/event-stream`; middleware сжатия в Hono SSE-маршрут обходит. Тесты (тикет «Доказуемость», #16): интеграционный на настоящем Postgres — открыть поток, получить первый снимок, сделать чекин на другом соединении → следующий снимок с `checkedIn + 1` в пределах 2 с; откаченная транзакция → снимка нет; e2e Playwright на два контекста — чекин в одном, цифра растёт в другом.

## D-022 — Код билета и однократный чекин: случайный код в регистрации, условный UPDATE (2026-10-20 10:58 +0700)
- Контекст: тикет «Билет и чекин» (#14). «Билет проходит чекин один раз»; сканер заменён вводом кода. Чекин делает только владелец события под своей сессией (D-005), строку события чекин не блокирует (D-011), live-счётчик срабатывает от триггера на `registrations` (D-020).
- Выбрали: код — 8 символов алфавита Crockford Base32 (цифры и латиница без I, L, O, U), `crypto.randomInt` на символ, 40 бит; показывается как `K7QM-4XPA`, при вводе приводится к верхнему регистру, пробелы и дефисы выкидываются, O читается как 0, I и L — как 1. Хранится нормализованным в `registrations.ticket_code`, уникальный индекс `WHERE ticket_code IS NOT NULL`; при коллизии (~10⁻⁴ на 10 000 билетов) транзакция повторяется обёрткой из D-009, как на `40P01`. Код выдаётся в момент, когда регистрация становится подтверждённой, — при распределении (D-011) или повышении (D-012); у листа ожидания кода нет; при отказе код остаётся в отменённой строке, но чекин его не принимает; повторная регистрация после отказа — новая строка и новый код (D-007). Перенос код не меняет. Отметка — колонка `registrations.checked_in_at timestamptz NULL` (триггер D-020 уже ловит её изменение). Просмотр: `GET /api/organizer/events/:id/tickets/:code` — только чтение: имя, фамилия, дата рождения, возраст на день события и флаг «младше минимального возраста» (D-008, D-017), статус, `checked_in_at`. Отметка: `POST /api/organizer/events/:id/checkin { code }` — один запрос `UPDATE registrations SET checked_in_at = now() WHERE event_id = $1 AND ticket_code = $2 AND status = 'confirmed' AND checked_in_at IS NULL RETURNING …`. Обновилась строка — `200`; нет — запрос по `(event_id, ticket_code)` объясняет почему: уже отмечен → `409 already_checked_in` с именем и временем первой отметки, отменён → `409 ticket_cancelled`, не найден или билет другого события → `404 ticket_not_found`. Два одновременных запроса с одним кодом: второй `UPDATE` ждёт блокировку строки, после коммита первого перепроверяет `WHERE` (READ COMMITTED) и обновляет ноль строк — получает `already_checked_in`. Снятие отметки: `DELETE /api/organizer/events/:id/checkin/:registrationId` — `UPDATE … SET checked_in_at = NULL WHERE id = $1 AND event_id = $2`, идемпотентно. Отказ после чекина закрыт: транзакция отказа (D-012) отменяет только `WHERE checked_in_at IS NULL`, иначе `409 already_checked_in`, страница личной ссылки показывает «Вы уже прошли на событие». Отказ и чекин одной регистрации одновременно сериализуются блокировкой её строки — проходит одно из двух. Окна чекина нет: отметить можно в любое время. Время в ответах — в поясе события (D-015). Чекин — под общей корзиной rate limit (D-006). Решено агентом как стандартная практика; пользователю заданы только вопросы D-023.
- Альтернативы: UUID или длинный токен — угадать нельзя и так, а набрать на входе 36 символов нельзя; 6 цифр — легко набрать, но 10⁶ вариантов и опечатка в одной цифре даёт чужой валидный билет; последовательный номер — угадывается, по номеру видно число регистраций; отдельная таблица `checkins` — история отметок не нужна, лишний JOIN и второй триггер для D-020; `SELECT … FOR UPDATE` и затем `UPDATE` — тот же результат за два запроса; блокировка строки события — сериализовала бы чекины всего события с регистрациями без нужды; отказ после чекина с уменьшением «Пришло» — человек уже внутри, а освободившееся место повышение отдало бы тому, кто не успеет прийти.
- Последствия: код короткий, но его подбор бессмыслен — чекин доступен только владельцу события, а карточка показывает имя и дату рождения для сверки с документом. «Пришло N» не уменьшается само, только снятием отметки. Перенос отметки не сбрасывает: если событие перенесли после начала чекина, организатор снимает их вручную (перенос возможен только до начала, D-016). Тесты — в тикете «Доказуемость» (#16).

## D-028 — Тесты: Vitest на настоящем Postgres из docker compose, e2e в Playwright (2026-10-20 19:13 +0700)
- Контекст: тикет «Доказуемость: тесты, e2e на две вкладки, CI» (#16). Требования задания держатся на транзакциях, блокировках и параллельных соединениях (D-011, D-018, D-022), поэтому доказывать их нужно на настоящем Postgres. Конкретные тест-кейсы уже записаны в последствиях D-006, D-011, D-013, D-018, D-020, D-022 и в комментариях к #16.
- Выбрали: раннер — Vitest с двумя проектами. `unit` — чистые функции: нормализация кода билета, backoff, шаблоны писем. `integration` — настоящий Postgres. Postgres и Mailpit берутся из `docker compose` (выбор пользователя): ревьюер выполняет `docker compose up -d`, потом `pnpm test` и `pnpm e2e`. Адрес базы — `TEST_DATABASE_URL`, по умолчанию compose-Postgres на localhost. Если база недоступна, тесты сразу падают с подсказкой «Запустите `docker compose up -d`». Глобальная подготовка один раз применяет миграции (`migrate(db)`, D-009) к шаблонной базе. Каждый воркер создаёт свою базу через `CREATE DATABASE … TEMPLATE`, между тестами — `TRUNCATE … RESTART IDENTITY CASCADE`. Откат транзакции для изоляции не годится: тесты гонки и чекина коммитят на разных соединениях. HTTP проверяется через `app.request()` (D-004). Письма в интеграционных тестах читаются из outbox, `dispatchOutbox` получает фейковый транспорт. Время передаётся параметром, без фейковых таймеров. Демо-сид тесты не используют (D-010). Обязательный список дополнен тестом повторной регистрации: два параллельных подтверждения одного email на одно событие дают одну неотменённую регистрацию (D-007). Гонку и напоминания проверяют только интеграционные тесты: в браузере временем не управлять без тестового входа в боевой сборке. E2e — Playwright, только Chromium. `webServer` запускает собранное приложение (один процесс, D-024) на отдельном порту, со своей базой, с поднятыми лимитами rate limit (D-006) и SMTP в compose-Mailpit. Каждый тест берёт уникальные адреса и ищет письма в API Mailpit по получателю, поэтому почта разработки не мешает. Три сценария (выбор пользователя): регистрация, где код читается из Mailpit, а в письме приходит билет; две вкладки — чекин в одной, «Пришло» растёт в другой без перезагрузки, повторный код показывает «Уже прошёл в …»; отказ по личной ссылке, после которого первый из листа ожидания получает письмо о месте. При падении сохраняются трейс и скриншот.
- Альтернативы: testcontainers — `pnpm test` без compose, но это ещё одна зависимость и несколько секунд на старт контейнера, а на macOS с Colima или OrbStack нужна настройка сокета Docker; Mailpit для e2e всё равно пришлось бы поднимать отдельно. Jest — ESM и TypeScript требуют отдельной настройки. Cypress — не открывает два независимых контекста браузера в одном тесте, а сценарий с двумя вкладками на этом и держится. Один e2e-сценарий (только две вкладки) — путь участника, первое, что пробует ревьюер, остался бы без проверки в браузере. E2e на каждое требование (около восьми) — почти ничего не добавляет к интеграционным тестам, съедает полдня и добавляет нестабильных тестов.
- Последствия: без запущенного compose тесты не идут — README ставит `docker compose up -d` первым шагом. Compose публикует порты Postgres и Mailpit на localhost. Тестовые базы живут в том же контейнере, что и база приложения, но данные приложения не трогают. Обычные лимиты rate limit e2e не проверяет — для этого есть отдельный интеграционный тест 429 (D-006).

- Контекст: тот же тикет. По письму в поддержку не понять, что пишет владелец регистрации: адрес отправителя легко подделать, а исправление даты рождения обходит проверку возраста (D-008).

Отправка создаёт заявку на исправление — таблица `correction_requests`: регистрация, старые значения на момент подачи, новые значения, `status` (`pending`, `accepted`, `rejected`, `withdrawn`), `reason`, `created_at`, `decided_at`, `decided_by`. На регистрацию не больше одной заявки `pending` (частичный уникальный индекс); новая подача переводит прежнюю в `withdrawn`, отказ закрывает ожидающую заявку в своей транзакции (D-012). Подача — в корзине «публичные действия участника» (D-006). Пока заявка ждёт, страница регистрации показывает «Заявка на рассмотрении» с предложенными значениями. Экран админа `/support` — очередь ожидающих заявок от старых к новым: событие, email, «было → стало» и предупреждение «Будет младше N лет на день события», если после правки участник не проходит по возрасту (D-017). «Принять» — одна транзакция: условный `UPDATE correction_requests SET status = 'accepted' … WHERE id = $1 AND status = 'pending'` и запись новых значений в регистрацию; ноль строк — `409` (заявку уже заменили, отозвали или решили). «Отклонить» — с необязательной причиной. Значения админ не меняет. Решение кладёт письмо участнику в outbox той же транзакцией (D-013): «Данные исправлены» с новыми значениями или «Исправление отклонено» с причиной. Отдельной истории правок нет: след — сами заявки (что было и стало, когда подано, кто и когда решил). Организатор видит текущие данные без отметки об исправлении. Экраны собираются из компонентов дизайн-шаблона (D-025, D-027), новой доски в Claude Design нет.
- Альтернативы: письмо на адрес поддержки — проще, но поддержка верит адресу отправителя, а на стенде путь не проверить: письмо уходит из почтовой программы ревьюера мимо Mailpit; прямая правка участником по личной ссылке — владение доказано, но исправление даты рождения после проверки возраста никто не видит (D-008); правка значений админом при приёме — админ не знает данных лучше участника; отдельная таблица истории — повторяет заявки.
- Последствия: новая сущность, два шаблона писем и три новых экрана: форма на странице регистрации, вход и очередь поддержки. Уведомления админу о новой заявке нет — только счётчик ожидающих на экране поддержки. Тесты: принять и отклонить с письмом, повторная подача заменяет заявку, два одновременных «Принять» дают один эффект, отказ закрывает заявку, организатор не достаёт `/api/support/*`.

## D-032 — Лимит мест ниже числа подтверждённых: билеты остаются, «сверх лимита» (2026-10-20 20:11 +0700)
- Контекст: тикет «Уменьшение лимита мест ниже числа подтверждённых» (#32). Было подтверждено 50, организатор ставит лимит 40. Отменить чужую регистрацию организатор не может: отказ — действие участника, поддержка отмену не трогает (D-030).
- Выбрали (выбор пользователя): сохранение разрешено, все подтверждённые остаются с билетами, писем нет. Новый лимит пишется в той же транзакции под блокировкой строки события (D-011), регистрации не меняются. Пока подтверждённых не меньше лимита, свободных мест нет: новые регистрации уходят в лист ожидания, а отказ подтверждённого никого не повышает. Повышения возобновляются, когда подтверждённых становится меньше лимита, — той же функцией «заполнить свободные места» (D-012), она уже повышает только пока подтверждённых меньше лимита. Инвариант «свободное место и непустой лист ожидания одновременно не существуют» сохраняется. Лимит — целое число от 1, сервер принимает любое такое значение и в ответе отдаёт свежий снимок счётчиков (D-020). Форма (выбор пользователя): если новый лимит меньше подтверждённых по последнему снимку, «Сохранить» открывает диалог подтверждения из шаблона (D-027): «10 подтверждённых сверх лимита. Билеты у всех останутся, новых мест не будет, пока подтверждённых не станет меньше 40. Сохранить?». Плашка организатора — «Подтверждено 50 из 40» с пометкой «10 сверх лимита» в предупреждающем цвете (D-021). Свободные места — ноль, участник видит «Мест нет — вы встанете в лист ожидания» (D-026). Уменьшение лимита без превышения ничего не меняет, даже при непустом листе ожидания. Изменение лимита после начала события решает тикет «Регистрация, отказ и повышение после начала события» (#33).
- Альтернативы: запрет сохранения, пока лимит меньше подтверждённых, — организатор застревает: ни одной чужой регистрации он отменить не может и ждёт, пока 10 человек откажутся сами; перевод последних по времени подтверждения в лист ожидания с письмом — отбирает выданный билет, требует правил для прошедших чекин и для повышенных (чьё время считать «последним»), нового письма и тестов; предупреждение под полем вместо диалога — пользователь выбрал диалог, чтобы превышение нельзя было сохранить не глядя.
- Последствия: на событие с билетами может прийти больше людей, чем лимит; если зал стал меньше, организатор договаривается с участниками вне сервиса. Лист ожидания ждёт дольше: повышение начинается только после того, как откажутся все, кто сверх лимита, и ещё один. Глоссарий: «Лимит мест» больше не обещает, что подтверждённых не больше лимита. Число в диалоге — из снимка и может устареть за секунды до сохранения; это безопасно, сохранение ничего не отнимает. Тесты (D-028): уменьшение 50 → 40 оставляет 50 подтверждённых с билетами и не шлёт писем; регистрация при превышении уходит в лист ожидания; отказ при 50 из 40 не повышает, при 40 из 40 после ещё одного отказа повышает первого из листа; снимок отдаёт `confirmed > limit`.


## D-033 — Начало события закрывает всё, что меняет места: регистрацию, отказ, повышение (2026-10-20 20:31 +0700)
- Контекст: тикет «Регистрация, отказ и повышение после начала события» (#33). Повышение работало «вплоть до начала» (D-012), отказ после чекина закрыт (D-022), перенос — только до начала (D-016), конца у события нет (D-015), изменение лимита после начала отложено сюда (D-032). - Выбрали (выбор пользователя): единственная граница — момент начала (`starts_at`). С этого момента закрыты новая регистрация, отказ (и из подтверждённых, и из листа ожидания) и повышение. - Последствия: подтверждённый, который не придёт, после начала не может об этом сказать — «Пришло 30 из 40» включает его. Опоздавший без регистрации не попадёт в систему, вручную добавить участника организатор не может. Тесты (D-028): после начала регистрация, отказ и подача заявки отвечают «закрыто»; отказ ровно до начала повышает первого из листа, после — запрещён; код, введённый после начала, места не даёт; вход по email и коду после начала открывает существующую регистрацию; лимит после начала не меняется.


## D-034 — Лист ожидания после начала: без письма, статус на странице по личной ссылке (2026-10-20 20:31 +0700)
- Контекст: тот же тикет. После начала повышений больше не будет (D-033), а в листе ожидания остаются люди.
- Выбрали (выбор пользователя): письма «мест не осталось» нет. Страница по личной ссылке (D-007) после начала: у подтверждённого — билет и «Событие началось», без кнопки отказа и формы исправления; у листа ожидания — «Событие началось, место не освободилось»; у отменённой — как раньше. Страница события после начала вместо формы регистрации и «Осталось N мест» (D-026) показывает «Событие началось — регистрация закрыта» и вход в свою регистрацию по email и коду.
- Альтернативы: письмо каждому из листа ожидания в момент начала — приходит, когда ждать уже нечего (время начала человек знает), а стоит ещё одного прохода по расписанию, шаблона и теста.
- Последствия: человек из листа ожидания узнаёт об итоге, только если откроет ссылку; требование «лист ожидания» этим не затрагивается. Сторож напоминаний (D-018) не меняется.
