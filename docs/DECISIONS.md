## D-001 — Как фиксировать ход работы (2026-10-19 14:50 +0700)
- Контекст: задание требует промпты, лог решений и видимую постепенность работы.
- Выбрали: три файла в `docs/` (хронология, решения, промпты) + правила для агента в `CLAUDE.md` (`AGENTS.md` — симлинк для других агентов). Промпты пишет хук, а не агент.
- Альтернативы: только экспорт сессии jsonl — не читается человеком и не показывает «почему»; один общий файл — решения тонут в хронологии; промпты руками агента — агент может пропустить или перефразировать.
- Последствия: хук работает только в Claude Code; экспорт сессии jsonl приложим к сдаче дополнительно.

## D-002 — Инфраструктура: свой бэкенд вместо Supabase (2026-10-19 17:20 +0700)
- Контекст: рассматривали Supabase как готовые Postgres + realtime + почту.
- Выбрали: свой бэкенд на Node + PostgreSQL + Mailpit (SMTP-заглушка с веб-UI), всё поднимается через `docker compose`.
- Альтернативы: Supabase — встроенный SMTP только для auth-писем (лимит ~2 письма/час, доставка только адресам команды проекта), то есть для билетов/напоминаний всё равно нужен свой SMTP; типичная схема «фронт → PostgREST + RLS» убирает Node-бэкенд, что конфликтует с требованием «Backend: Node.js», и уводит критичную логику (гонка за место, повышение из листа ожидания) в SQL-функции; облако требует аккаунт и ключи, локальный `supabase start` — ~10 контейнеров.
- Последствия: live-обновления (SSE/WS + `LISTEN/NOTIFY`) и отправку почты пишем сами; Mailpit даёт наблюдаемые письма для проверки и тестов.

## D-003 — Рантайм Node, пакетный менеджер pnpm, не Bun (2026-10-19 17:20 +0700)
- Контекст: рассматривали Bun как рантайм и тулинг.
- Выбрали: Node 22 LTS, pnpm (workspaces для backend/frontend).
- Альтернативы: Bun как рантайм — это отдельный рантайм (JavaScriptCore, Zig), лишь совместимый с Node API; буквальное требование «Backend: Node.js» нарушается. Bun только как тулинг — серая зона и ещё одна зависимость в предусловиях. npm — медленнее и без строгой изоляции зависимостей.
- Последствия: предусловия — Node 22, pnpm (через corepack), Docker.

## D-004 — HTTP-фреймворк: Hono на Node (2026-10-19 17:20 +0700)
- Контекст: выбор между Hono, Fastify, Express 5.
- Выбрали: Hono через `@hono/node-server`.
- Альтернативы: Fastify — зрелый продакшн-стандарт, но больше церемоний и нет типизированного клиента; Express 5 — слабые типы, валидацию/SSE собирать вручную.
- Последствия: встроенный `streamSSE`, `@hono/zod-validator`, тесты через `app.request()` без поднятия сервера, типизированный RPC-клиент `hc` во фронте (общие типы API). Экосистема под Node меньше, чем у Fastify/Express.
